# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

MimicAgent: an LLM agent (LangGraph + Claude) that turns a natural-language robot skill description into motion-generator code, executes it in a MuJoCo simulator, checks the resulting trajectory, and iteratively repairs the code. The top level has four areas:

- `robots/<name>/` — per-robot CODE + spec (`robot.yaml`, `example.py` reference, and `exemplars/` — a couple of curated hand-authored reference skills, tracked). The MuJoCo assets live under `assets/` (below).
- `assets/robots/<name>/` — MuJoCo model + meshes (the model owns its `<keyframe home>`); `assets/scenes/` — **robot-AGNOSTIC** environment scenes (`flat.xml` default + `slab/stairs/carry/chair.xml`), floor + objects only, no robot. The sim **composes** a robot + a scene at load (`simulator/utils/scene_compose.py`), so any scene works with any robot.
- `simulator/` — the MuJoCo kinematic simulator that drives a robot with a skill and records a trajectory
- `agent/` — the LLM pipeline that writes skills (was `mimic_agent/`)
- `skill_output/<robot>/` — generated skills + artifacts (gitignored)

`docs/ARCHITECTURE.md` is the long-form companion (worked examples, adding-a-robot walkthrough) and `README.md` the short one; both were brought in sync with this file, but **this file wins on any conflict** — it is the one loaded automatically. `archive_output/` holds prior runs and is neither tracked nor gitignored.

`robots/<name>/robot.yaml` is the **single source of truth** for a robot (end-effectors, joints + limits, passive joints, base-height envelope, camera, prompt "robot card"). Both halves read it; nothing else hardcodes morphology. This repo ships the **humanoid** only (28 DoF; feet + hands are IK end-effectors, arms/torso/neck default to joint-driven via `joint_overrides`, plus a MAXIMAL contact roster of extra `contact_bodies` in the UNION IK roster).

## Commands

Run everything **from the repo root** (the simulator resolves data paths relative to the repo root; the agent runs its subprocess with the repo root as CWD).

```bash
pip install -r requirements.txt
export ANTHROPIC_API_KEY="..."

# Simulator: play a robot's reference skill (default mode = "example")
python simulator/run.py --robot humanoid --record True
python simulator/run.py --robot humanoid --mode example --record True

# Simulator: play a generated or curated skill. `--mode` resolves a GENERATED skill
# first, then a curated exemplar (matching the controller's own load order), and
# reads that skill's scene + grounding + repetitions from its motion plan — so a
# bare replay REPRODUCES the agent's recording. Override any of the three
# explicitly; precedence is  CLI flag > the skill's plan/exemplar > config default.
python simulator/run.py --robot humanoid --mode SKILL_CLIMB --record True
python simulator/run.py --robot humanoid --mode SKILL_WALK \
  --scene assets/scenes/stairs.xml --grounding off --record_cycles 4 --record True

# Agent: single skill from natural language (the ONLY entry point; no batch mode)
cd agent && python run.py --skill "The humanoid walks forward" --name SKILL_WALK

# Re-score every shipped skill against the SAME evaluator the pipeline uses.
# `finalize` deletes the per-iteration report_*.json, so this is the only way to
# answer "did that framework change help?". --json snapshots, --compare diffs.
python agent/score_skills.py --json before.json
python agent/score_skills.py --compare before.json

# Interactive Streamlit demo
cd agent && streamlit run app.py
```

Per-robot generation tools — run once when a robot is added, never in the loop:

```bash
python simulator/tools/gen_robot_spec.py    --robot <name>   # -> robots/<name>/robot.yaml (scaffold, has # REVIEW marks)
python simulator/tools/gen_robot_summary.py --robot <name>   # -> summary.md + dynamics.json
```

Debug tools, all reusing the same `MotionControllerRunner` as the live sim, so what they measure is what plays:

```bash
# Reachability oracle: replays the skill's step() over one cycle with NO IK/render and
# reports which declared world contacts are out of limb reach. The pipeline calls this
# BEFORE every sim rollout; run it by hand to debug a "PRE-SIM LINT FAILED" message.
python simulator/tools/reach_lint.py --mode SKILL_X --robot humanoid --grounding off

# Offscreen mp4/gif render (no display). finalize() calls this for the preview GIF.
python simulator/tools/record_video.py --robot humanoid --mode SKILL_X --out /tmp/x.gif

# Live viewer for dialling in a named stance by hand (exports paste-ready YAML).
python simulator/tools/pose_editor.py --robot humanoid
```

Environment toggles: `SKIP_SKILL_FILTER=1` bypasses the feasibility gate for explicit `--skill` runs; `ROBOT_NAME=<name>` overrides `cfg["robot"]["name"]` per process, so two robots can generate in parallel without editing the shared `config.yaml`. Simulator nets, all default ON, each disable-able for A/B: `REACH_PROJ=0`, `SEAM_BRIDGE=0`, `SEAM_BRIDGE_JOINTS=0`, `GROUNDING_CLAMP=0`, `RATE_LIMIT=0` (the physical slew limit), `CONTINUITY_REF=0` (null-space continuity prior), `EE_ORIENT=0` (the rotational IK task). Tunables: `IK_HOME_PULL` (0.05), `IK_ORI_WEIGHT` (0.4), `IK_BACKEND` (`dls`|`mink`).

There is no test suite. `agent/utils/test_motion_quality.py` is not pytest — it is the trajectory-quality checker run by the pipeline's unit-test node.

Caveats for running:
- Robot MuJoCo models (MimicKit-style) live under `assets/robots/<name>/` (model + meshes + its own `<keyframe home>`); scenes are **robot-agnostic** environments under `assets/scenes/` (`flat.xml` + `slab/stairs/carry/chair.xml`). `simulator/utils/scene_compose.py:compose_model(robot_mjcf, scene_env)` writes a tiny wrapper IN `assets/scenes/` that `<include>`s both, so MuJoCo resolves `meshdir` (relative to that wrapper — models with meshes use `meshdir="../robots/<name>/assets/"`) and the env `<include>`. `run.py` (via `MujocoSimulator(..., robot_mjcf=spec.mjcf)`) and `gen_robot_summary.py` both compose. **The `⚠️ Site not found` warnings at startup are expected**: the humanoid's 4 EEs have `ee_*` sites in the MJCF, but the 11 `contact_bodies` declare no `site:`, so `contact_body_sites` falls back to the body name and IK aims at the body origin (the `ground_offset` carries the vertical). Expect `[IK] Sites found: 4/15`.
- The simulator opens a glfw window — it needs a display. Pass `--headless True` (what the agent does) to skip glfw/GL and the real-time throttle entirely; `tools/record_video.py` and `tools/reach_lint.py` are also display-free.
- **CWD must be the repo root.** `simulator/run.py` puts its own dir on `sys.path` (so `from core...`, `from utils...`, `from motion...` resolve), but data paths (`robots/...`, `skill_output/...`) are repo-root-relative. The agent selects the robot once in `agent/cfg/config.yaml` (`robot.name`) and passes `--robot` to the simulator subprocess, so the two halves can't disagree.

## Architecture

### Robot spec (`robots/<name>/robot.yaml` → `simulator/utils/robot_config.py:RobotSpec`)

Everything morphology-specific lives here: `end_effectors` (ordered `{name, body, site, ground_offset}` — the names are what skill code and prompts use, no normalization layer; `contact: false` excludes an EE from the ground/penetration checks, `wheel: true` lets a planted EE roll without being XY-pinned), `contact_bodies` (the extra weight-bearing bodies — pelvis, torso, head, knees, thighs, forearms, upper arms — same `{name, body, ground_offset}` shape; **EEs + contact_bodies = the UNION IK ROSTER**), `joints` (in **model qpos[7:] order** — the recorder and quality checks depend on this; `passive: true` marks unactuated joints like a wheel), `base_height_range`, `camera`, `sim_freq`, `mjcf`, `null_space_gain` (how hard IK pulls back toward the rest pose — lower it on a high-DoF robot so limbs can reach far), `example_skill` (path to the robot's reference skill), and `robot_card` (free-text morphology description injected into every prompt — **KINEMATIC FACTS ONLY**: DoF, end-effectors, pelvis height, and each joint's axis + sign + range. It deliberately says NOTHING about which control channel a limb uses — that is the agent's decision, made per limb per phase; no heuristics/pose-cookbooks live here). Two optional sections: `environments` (named scenes a skill may run in — `{name, scene, grounding, objects}`; a `flat` default is always implied; the planner picks one, the executer runs the sim with that scene + grounding, and `RobotSpec.get_environment` resolves it — **beware YAML parsing `grounding: off` as boolean `False`, so quote it**) and `exemplars` (curated reference skills — `{name, environment, tags, summary}`, each backed by `robots/<robot>/exemplars/<name>.py`; `RobotSpec.get_exemplar` resolves it, and `run.py` auto-loads the exemplar's scene when you play it by `--mode`). Paths inside the yaml (`scene_xml`, `mjcf`, `example_skill`, environment `scene`) are repo-root-relative. The controller asserts at startup that the YAML joint order matches the model's qpos order.

### Agent pipeline (`agent/`)

LangGraph state machine built in `agent/run.py` over `agents/code_gen/state.py:AgentState`:

```
skill_filter → motion_planner → code_generator → code_executer → unit_test_router
                    ↑                                 ↑                 │
                    │                            critic_coder ← motion_diagnosis
                    │                                 ↑                 ↑
                    └── replan ──────────────────  (repair)      critic_router ← unit_test
                                                                        │
                                                       finalize (best version) → END

unit_test_router:  clean run          → unit_test
                   lint_fail_streak≥2 → motion_planner   (REPLAN, once)
                   crash / lint fail  → critic_coder     (repair)
                   out of iters       → finalize
critic_router:     rewrite_mode=none  → finalize
                   stuck              → motion_planner   (REPLAN, once)
                   otherwise          → motion_diagnosis → critic_coder
```

`unit_test_router` and `critic_router` are pure routers (`lambda state: state` + a conditional edge). **`replan` fires from both sides and is capped at once per skill** (`state["replanned"]`) — it is the "step back and re-decide" a code rewrite structurally cannot do. `skill_filter` can veto straight to `END`.

- `code_executer_agent.py` is the bridge to the simulator: it extracts Python from the LLM message, writes it as `skill_output/<robot>/<SKILL>/<SKILL>_NNNN.py` (auto-incrementing), then runs the simulator via `subprocess` (`python simulator/run.py --mode <skill> --robot <robot> --record True --headless True --grounding <mode> --record_cycles <N>`, cwd = repo root). **Headless** (`--headless`) skips glfw/GL/real-time throttle entirely — no window, no display needed, ~10× faster — since the pipeline only needs the recorded pkl. `--record_cycles` comes from the plan's `repetitions` (clamped 1–8): a cyclic skill authors ONE cycle at `self.freq = 1/period` and the framework records N of them, so a walk travels several strides instead of one stride stretched over the whole clip. On a runtime crash it increments `num_critic_iters` and reports `success=False`.
- **Pre-sim reachability lint** (`run_reach_lint` → `simulator/tools/reach_lint.py`) runs *between* writing the file and the rollout. It rebuilds the same controller, replays the skill's `step()` over one cycle with no IK and no rendering, and checks that every declared world contact is within its limb's reach from the authored base — milliseconds instead of a minutes-long doomed rollout. Only a **hard** violation (one the runtime reach-seat cannot absorb) short-circuits; softer ones fall through to the sim. A hard fail returns `success=False` with the report as the message, plus a **signature** of what it caught (`arr:<ee>@<phase>`, `incompat@`, `horiz:`, `notgt:`). It also hard-fails a **DECLARED CONTACT THAT TRANSLATES** (`SLIDE_GROSS_M`=0.25 m of authored movement within one continuous declared-contact run — 2.5× the scored `contact_no_slide` budget, so only unambiguous cases short-circuit and a marginal drift still falls through). A contact is a limb held STILL against the world; one whose AUTHORED target slides was never released, so the robot is gliding rather than stepping. It reads ONLY authored targets, so a tracking error the solver introduces is never blamed on the author. Measured on a carry-box: BOTH feet declared contacts on **2000/2000 frames** while the base advanced 1.05 m — no gait at all; `contact_no_slide` caught it only after a full rollout, and the loop then spent its whole budget on the resulting floor failure instead of on the grip the skill was about. **Exemptions come from the SAME sources the scored law uses**, so oracle and test can never disagree about what is legal: spec `wheel: true` EEs (a wheel rolls), plan `sliding_contacts` (a skate/drag IS the skill), and plan `mode: pivot` (a pirouette spins on the spot) — without those the law would forbid legal motions, i.e. make the framework the ceiling rather than the physics. Verified: it flags the five skills that genuinely drag (carry-box 1.11 m, climb 0.58, ledge-drop 0.50, cartwheel 0.40, siuuu 0.40) and does NOT flag the reference walk, stairs, sit-chair, ballet or either flip. It also hard-fails a **DECLARED CONTACT WITH NO SURFACE BENEATH IT** (`NO_SURFACE_M`=0.25 m, well clear of the framework's own 5 cm floor-assist slack; checked in BOTH directions — a limb can bear load against a surface ABOVE it just as legitimately as one below (a bar hang, a pull-up, brachiation, a ceiling brace), so a down-ray alone would hard-fail every one of those pre-sim; only a contact with nothing near it in EITHER direction is flagged) — reach and arrival both assume the contact POINT is legitimate and only ask whether the limb can get there, so a skill standing at a ledge's HEIGHT before the ledge's EDGE passed every existing check and walked on thin air: measured on a ledge-drop, both feet declared as contacts at z=0.86 with **0.81 m of empty space below them** for the first 3 s (the slab only starts at x=1.05 and the robot started at x=0), then a fall at **−74 m/s², 7.6× gravity**. `contact_grounded` caught it only AFTER a full rollout and the loop then spent 10 iterations failing to fix it; one ray-cast per declared contact catches it in milliseconds. It also hard-fails a **chronically unreachable FREE limb** — gated on severity *and* persistence (beyond `FREE_SEVERE`=1.25× reach on more than `FREE_BAD_FRAC`=10% of frames), because a brief over-reach is absorbed by the runtime projection while a sustained one means the skill's intent is silently truncated for most of the motion. This is well-calibrated against the archive: `example`/`STAIRS`/`CRAWL` score 0.0, while HANDSTAND (hands at 1.99× reach on 13.9% of frames) and CARTWHEEL (43–45%) are caught in milliseconds — the two skills that previously burned 18 and 17 iterations without ever converging. Two consecutive *identical* signatures mean the coder is patching around a structural **plan** bug, so `unit_test_router` takes the replan edge instead of looping the coder. A clean sim run resets `lint_fail_streak`.

**`run_unit_test.py`** loads the recorded eval pkl (`skill_output/<robot>/<skill>/<skill>.pkl`) and scores it with `agent/utils/test_motion_quality.py`. The suite has **three tiers**, and the distinction matters — it is what stopped the loop from either shipping a legal-but-wrong motion or Goodharting its own tests:

1. **PHYSICS FLOOR** (`GENERIC_CORE` in `run_unit_test.py`) — universal laws, always on, pass/fail, the primary term of the version score.
2. **GATED** — same category (`discrete`), but each self-skips when out of domain, gating **only on physical declarations** (a `[]`-contact segment, scene objects present) — never on an editorial skill label.
3. **AGENT-DECLARED FIDELITY INVARIANTS** (`category: "fidelity"`) — the "does it actually *look* like the intended motion?" layer the pass/fail floor cannot express.

Floor: **surface_penetration** (fundamental collision — a robot geom CENTER below the floor OR inside a *static* scene box; false-positive-free on resting contacts; mocap manipulands excluded); **self_collision** (`mj_geomDistance` over non-adjacent robot geom pairs — the model filters self-collisions so `mj_collision` can't see them; now **SOFT**, gross-overlap only, since a graze is not a physics violation in a kinematic sim; and it **NAMES THE PAIR** via the recorded `collision_pair`, exactly as `surface_penetration` names `penetration_body`/`penetration_surface` — a bare scalar plus "separate the limbs" is unactionable when the offending pair is not the one the author would guess: a sit-chair regeneration spent its ENTIRE 10-iteration budget on a 10 cm shin-shin cross caused by SWAPPED knee-target signs (`right_knee` authored at y=+0.061, `left_knee` at −0.058), correctly isolating it as the sole remaining failure and trying three different levers — arms, foot-pelvis gap, torso pitch — but never the knees, because nothing ever named them); **support_or_ballistic** (skill-agnostic support law: at every frame a DECLARED contact must be resting on its surface, OR the skill must declare flight (`contacts==[]`) and the base be ballistic (accel ≈ −g) — sustained unsupported hover fails; handstands/one-leg/N-legged pass); **contact_grounded** (the per-contact companion: *every* EE/body DECLARED a contact must actually rest on its surface, not just some of them — `support_or_ballistic` is satisfied by one resting limb, so without this a crawl could declare four contacts and float three); **contact_no_slide** (over each FIRMLY-planted stance run — declared contact AND clearance ≤ 3.5 cm — net horizontal drift < 10 cm; a wheel rolls, a pivot spins in place, a moonwalk/drag fails); **joint_limits**; **no_teleport** (skill-agnostic continuity law: no actuated joint may STEP discontinuously between adjacent frames — an ISOLATED single-frame spike above a physical slew ceiling fails, a spike ~4× the ceiling is gross and fails regardless of count; sustained fast-but-smooth motion and the seam-bridge's own crossfade are NOT flagged, via LOCAL-neighbour isolation — this catches the control-channel-handoff pop, the "abrupt pose change" a semantically-correct skill still shows; the joint slew ceiling is per-joint fps-aware (rad/s × dt), not a fps-blind rad/FRAME floor; its feedback names a free-limb-out-of-reach cause when `reach_proj` fired near the pop); **ee_no_teleport** (the EE-SPACE companion — a FREE limb whose achieved position jumps ~1 m/frame BASE-COMPENSATED relative to a stationary torso, invisible to the joint-only check; catches the hand flicker from an out-of-reach free IK target); **joint_velocity_envelope** (physical: no actuated joint may SUSTAIN a speed above its torque-derived ceiling — its p90 velocity > 1.5× the per-joint ceiling in `robots/<name>/dynamics.json`, generated by `gen_robot_summary` from τ=I·q̈; complements no_teleport by catching SUSTAINED infeasible velocity a policy can't track, not a lone spike; a brief whip/kick passes; **self-skips** when the MJCF carries no torque source); **framework_interventions** (an OBSERVABILITY law — the simulator silently corrects impossible authoring via the target clamp / reach-seat / floor assist / reach projection, so a SATURATED correction means the authoring was impossible and must be surfaced, not hidden); **clip_duration** (a sub-2 s recording is a snippet, not usable motion data). Note `base_height_envelope` was **demoted** out of the floor into the declarable `base_height_band` invariant — a crouch/crawl/jump legitimately leaves any fixed band, and its one real job (hover/burial) is already covered by support + penetration.

Gated: **flight_window** (domain: a `[]`-contact segment; judged as the ballistic RISE above the takeoff surface, so a hop onto a slab is terrain-independent), **object_grip** (a lifted object must stay coincident with SOME end-effector — morphology-agnostic, no name-match), **object_continuity**, **object_at_rest** (object doesn't spawn mid-air; the end state is skill-specific, not asserted), **object_penetration** (a carried object must not clip through the body); **object_unheld_no_rise** (a GENERAL physics law and the object-side companion to `support_or_ballistic`: an object NOTHING is holding may fall, rest, or FLY BALLISTICALLY, but may NOT climb UNDER POWER — while unheld and rising its vertical acceleration must be ≈ −g. The ballistic exemption is not a softening: a thrown ball, a kicked can and a tossed crate all legitimately climb untouched, and forbidding that would make the FRAMEWORK the limit on what a user can ask for rather than the physics. This was the one levitation nothing forbade — `object_at_rest` only rules out SPAWNING mid-air (its docstring explicitly declines to forbid floating-unheld), `object_continuity` only rules out a velocity discontinuity so a SMOOTH rise passes, and `object_grip` is satisfied once object and limb coincide however they came to. Holders are **END-EFFECTORS ONLY**: the recorded roster is the UNION, and counting a KNEE as a holder silently excused the exact case this exists to catch (the crate sat at z=0.12 with the nearest body a knee 0.226 m away, inside tolerance, so its 0.12 → 0.50 m jump to meet a hand read as 'held'). Judged on CUMULATIVE unheld rise with no frame budget — a teleport is by definition a large jump over FEW frames, so a budget would defeat the law). All read the recorded `contact_mask` / `surface_clearance` / `object_pos`. There are **no skill-label test gates** (the old `motion_type`→`foot_clearance` gate and 8 superseded evaluators were deleted — prompts and tests are general laws + mechanisms, the agent makes every skill-specific decision).

**Fidelity invariants** are composed by the planner from eight general geometric primitives — `net_progress`, `peak_rise`, `swing_lift`, `phase_offset`, `base_height_band`, `object_coincident`, `end_state`, `stance_no_drift`, `contact_over_surface`. **`contact_over_surface` is MANDATORY for any goal that puts a body part ON a named surface** (sit on the seat, plant a foot on a tread, mantle a ledge): it binds the contact body's **xy to the surface's real footprint**, which a HEIGHT band cannot express and which a degenerate motion satisfies without ever going near the thing — measured on a sit-chair, the pelvis reached exactly seat height (0.56 m for a 0.45 m seat + 0.09 m offset) while standing at x=0.98, **19 cm IN FRONT of a seat spanning [1.17, 1.63]**, declared ZERO pelvis contacts, and scored a CLEAN physics floor for squatting in mid-air beside the chair. Height says how low; this says WHERE. The primitives are universal relations; all the skill-specificity is in *which* ones the planner picks and with what parameters, exactly like the control-channel decision. **Governance matters here**: invariants are **planner-owned** and are read from `motion_plan_*.json`, never from the code — otherwise the critic-coder would be the repairer editing the test it keeps failing. If diagnosis concludes an invariant is itself wrong, the loop must go through the **replan** edge to have the planner re-declare it. The planner also owns `sliding_contacts` (a full exemption from the no-slide law) and per-contact `mode: pivot` (a bounded drift budget, so a real pirouette passes but a runaway "pivot" still fails).

`run_unit_test` also builds a **motion readout** (`agent/utils/trajectory_readout.py`): a few paragraphs of pure geometry — base path, per-limb contact timeline + lift + drift, gait phase offsets, object path — fed to diagnosis and the critic. This is *perception before verdict*: the loop's deepest flaw was that the critic saw only a vector of pass/fail lamps, never the motion, so it local-patched and the checks fought each other. A per-version `version_history` line (score, floor failures, fidelity met) makes cross-version oscillation visible too.

**The loop continues while EITHER tier is unmet.** `rewrite_mode` is `structural` (floor broken) → `fidelity` (floor clean but it doesn't look like the skill) → `none`. Without the fidelity tier driving repair, the loop exited the instant the floor was clean — a carrybox that had picked the box up but let it drift out of the hands shipped at 4/6.

**Version-selection**: `run_unit_test` scores each version `generic_pass·1000 + passed_all_discrete·100 + 40·fidelity_fraction + reward − core_severity`. The fidelity weight drops to 2.0 until the version clears the **PHYSICS FLOOR** — and the gate is `generic_pass`, **NOT** `passed_all_discrete`. `passed_all_discrete` also contains the TASK checks (`object_grip`, `object_continuity`, `flight_window`), which measure the same thing the fidelity tier does — did the skill actually DO the thing — so keying on it meant **FAILING THE TASK SUPPRESSED THE VERY TERM THAT MEASURES THE TASK**, a feedback loop with the wrong sign. Measured on a carry-box: physics floor clean (+1000), `object_grip` failed, so fidelity was weighted 2.0 and contributed **1.1 points out of ~1000** — any version that gripped the box but scuffed one physics check would lose 1000, so the loop rationally shipped a physically-valid motion that never picks the box up. The tiers strictly dominate, so an invariant can never outrank a floor failure (40 < 100 < 1000). The **severity** term (normalized magnitude of the failed core checks, <1) breaks reward ties so a nearly-fixed version outranks a badly-broken one with the same failure COUNT (without it, the loop shipped v1-worst over v6-repaired); `>=` tie-break keeps the LATEST. There is deliberately **no early stop-loss** — a fidelity fix that briefly regresses something must still be allowed to keep experimenting; termination is the iteration cap, the one-shot replan, and finalize.

**Recoverability** hangs on one flag, `stuck`, set in `run_unit_test` and read by *both* `critic_router` (the replan decision) and `motion_planner_agent` (the replan context) so the two can never disagree: the overall score plateaued for ≥2 iterations (`no_improve_count`), **OR** any single core test has been failing ≥3 versions in a row (`core_fail_streaks`). The per-test streak exists because the overall score can tick up on an unrelated severity change while one specific check stays dead for iterations — carrybox's `object_grip`, crawl's `contact_grounded` ×6 — so `no_improve` kept resetting and the loop never replanned. A replan is fed the previous plan, the readout, and the version history, so it diffs rather than starting blind; the diagnosis taxonomy is open (+ an interface-mismatch class) and the critic may switch a limb's channel.

Remaining pieces:

- `skill_filter` gates feasibility with an LLM call; set env `SKIP_SKILL_FILTER=1` to bypass it for explicit user-requested `--skill` runs (e.g. aerial/expressive moves the gate would otherwise veto).
- Everything a skill generates lives in one dir, `skill_output/<robot>/<skill>/`. **During** the loop that is per-iteration: `<skill>_NNNN.py`, `<skill>_NNNN_prompt.md` (the exact prompt that produced that version), `motion_plan_NNNN.json`, `report_NNNN.json`, plus the trajectory `<skill>.pkl` + `_mimickit.pkl` and `metadata.json` (tokens + wall time).
- `make_finalize_node` is where a run becomes a deliverable, and it does four things in order: (1) copies the **best-scoring** version — not the last — to a new highest number, since the loader always takes the highest; (2) **always** re-runs the sim under the resolved environment and warns loudly if that re-run fails, so a stale pkl from a different version can never ship silently beside the wrong code; (3) renders a preview GIF via `simulator/tools/record_video.py` (best-effort, never fails the run); (4) ships clean `<skill>.py` + `<skill>_prompt.md` + `<skill>_plan.json` and **deletes every per-iteration intermediate**. So a finished dir looks nothing like a mid-run one — `simulator/motion/__init__.py:_find_latest_skill_file` handles both, preferring a versioned `<skill>_<N>.py` when present (a run in progress) and falling back to the clean `<skill>.py` (finalized).
- Config: `agent/cfg/config.yaml` — LLM model, `robot.name` (overridable per-process by `ROBOT_NAME`), four paths (`prompts_dir`, `robots_dir`, `simulator_dir`, `skill_output_dir`), `critic.max_iters` (7 — the floor alone can consume 5, and the once-only replan needs room after it). `load_yaml_config` resolves those paths relative to `agent/`'s parent, i.e. the repo root.
- Prompts: a single flat template set in `agent/prompts/templates/*.txt` (`=== SYSTEM ===` / `=== HUMAN ===`). `prompts/prompt_loader.py:load_prompt` fills the RobotSpec placeholders via `str.replace` (never `.format` — templates contain literal JSON braces): `{robot}`, `{urdf}`, `{end_effectors}`, `{num_end_effectors}`, `{support_set}` / `{free_ees}` (contact EEs vs. the rest), `{contact_bodies}`, `{contact_offsets}` (an explicit per-contact `ground_offset` table **plus the arithmetic** — a declared contact's world z is `surface_height + ground_offset`, never the bare surface height; this one substitution exists because authoring a contact at z=0 on the floor was the single most-repeated bug), `{joint_order}`, `{joint_limits}`, `{base_height_range}`, `{morphology_card}`, `{example_skill}`, `{base_class_source}` (reads `simulator/motion/base.py` live), `{robot_summary}` (a physical summary — limb lengths, per-EE reach, **per-joint position limits**, and — auto-emitted when the MJCF carries mass/inertia + torque limits — per-joint velocity/acceleration ceilings plus grounded, cited torso forward-speed/jump/roll-pitch-yaw-rate estimates; pre-generated by `simulator/tools/gen_robot_summary.py` into `robots/<name>/summary.md`; keeps commanded amplitudes *and velocities* physically feasible. The physics lives in `simulator/utils/robot_dynamics.py`), `{environments}` (the named scenes from `robot.yaml`, **each annotated with its real geometry** — per-step tread heights, slab extents, box pose, and the distance from the robot's home keyframe — parsed straight out of the scene XML by `agent/utils/scene_geometry.py`. Before this, the agent got only a name and a hand-written blurb, so it *guessed*: it climbed 2 of 5 steps, planted feet where no tread was, and modeled a finite staircase as a cyclic gait), `{exemplars}` (a catalog of the robot's curated reference skills — name, tags, technique). Per-call placeholders (`{{MOTION_SPEC_INPUT}}`, `{SKILL_NAME}`, `{USER_SKILL}`, …) are filled later by the nodes. The **motion planner** emits one JSON plan: `environment`, `cyclic`, `duration_s` + `repetitions` (one authored cycle × N recorded — total clip is the product, a distinction the prompt labours because getting it backwards records 28 s instead of 4.8 s), `phase_definition.sub_phases` (**the canonical timeline — `contact_schedule`, `free_limb_mode`, and `base_motion.per_phase` must all tile [0,1] with exactly these boundaries**), `contact_schedule` (per-phase declared contacts, surface, planted|pivot mode), `free_limb_mode` (per free limb, chosen by the agent: `world_reach` | `body_swing` | `joint_posture` | `none`), `fidelity_invariants`, and `sliding_contacts`. The channel decision is the AGENT's, made per limb per phase from a general **coupling principle** in the prompts (a limb whose endpoint is fixed by the world or by a thing it grips/holds → world-IK; a limb whose shape is the point → joint) — no prompt prescribes a channel for any limb. `coder_agent.py:_channel_table` deterministically expands the plan's choices into an explicit per-limb method table; `_environment_context` adds the scene's objects + grounding + the `attachments()` recommendation; `_plan_lint` flags an internal contradiction (an object is carried but no limb is world-bound to grip it) and licenses the coder to override a mislabeled channel; and the coder is shown the **full source** of a curated exemplar whose environment matches. The old velocity-only / body-frame-only / cyclic-only planner prohibitions are gone — absolute world-frame base trajectories and one-shot (non-cyclic) skills are first-class.
- **CONTACT REACHABILITY (the planner-reach law).** The planner used to choose a contact schedule and a base trajectory *independently* and never check they were compatible — so every hand-planting skill (cartwheel, handstand, vault, wall-kick) was planned unbuildable and only discovered downstream, after a rollout. `gen_robot_summary` now emits a `reach` block into `dynamics.json` (per-EE `reach`, `ground_offset`, and the full body-frame `root_off`), `{reach_envelope}` injects it into the planner prompt as a derived table, and `coder_agent.py:_plan_lint` checks the plan's own numbers **before any code is written**. The plan schema carries numeric `base_height_m`, `surface_height_m` and `torso_pitch_deg` for this; free text like `torso_height: "~0.9 m upright"` cannot be checked.
  - **It is orientation-dependent, and that is the whole point.** The limb-root offsets are BODY-frame, so they rotate with the torso: the humanoid's shoulder sits 0.48 m *above* an upright pelvis and 0.48 m *below* an inverted one. A hand can reach the floor with the base at ≤ 0.09 m upright, ≤ 0.55 m at 90°, ≤ **1.05 m inverted**. A cartwheel reaches the ground by *inverting*, not squatting. Judging an inverted phase by the upright bound flags a CORRECT plan as broken and pushes the planner toward a worse one (measured: 6 false positives on a good plan). When `torso_pitch_deg` is absent and the orientation text is not clearly upright, the check **says nothing** rather than guessing.
  - The check is **full 3-D** (`_reach_violation`, one implementation shared by every world-fixed target) and it **decomposes the failure**, because the fix differs: if the purely horizontal distance already exceeds the limb's reach, no base height helps and the base must move in x/y; otherwise it reports the exact feasible base height. It uses the same `1.03` gate as the runtime reach-seat — a humanoid's standing pose sits at ~100% of leg extension, so flagging at >1.00 reports the robot standing still as an error.
  - **It covers GRIPS too, not just contacts.** A limb that must coincide with something it grips is the same geometry problem as one planted on a surface, but it is declared in `free_limb_mode` (channel `world_reach`), so the contact-only version never saw it. Measured consequence on a carry-box: the hands stopped **0.44 m above** a box resting at z=0.12 and **the box levitated up to meet them** — `object_grip`'s `picked_ok` failed at 0.283 m against a 0.239 m tolerance. The envelope this yields is exactly how a human lifts a floor box: gripping a box at 0.12 m needs the base at ≤ 0.17 m upright, but ≤ 0.53 m with the torso pitched 80° — i.e. **bend over, don't squat**.
- **BALLISTIC FEASIBILITY (the flight law).** The same class of error as the reach law, on the other axis: the planner picks a flight phase and the base heights around it *independently*, and nothing checked that gravity connects them. In flight the base is unpowered, so `z(t) = z0 + v0·t − ½g·t²` — duration and height change are ONE decision. `_plan_lint` solves for the required launch velocity and compares it to `sqrt(2·g·jump_height)` from `dynamics.json`. Measured on the ledge drop: a declared 1.63 → 0.65 m over **1.20 s** needs a **+5.07 m/s** launch against a **2.20 m/s** maximum (2.3×), so the "jump" was really a slow lowering at −2.2 m/s² and `support_or_ballistic` rejected the whole window — it was that skill's last surviving floor failure. The message reports the physical range (0.45 s as a pure drop, 0.72 s with a full jump). Self-skips when the plan has no `duration_s` or the robot has no jump data.
  - Plans carry `base_height_m`, `surface_height_m`, `torso_pitch_deg`, `offset_from_base_m` and (for a `world_reach` limb) `target_height_m` so all of this is mechanically checkable. **Both checks are fail-open**: a plan omitting a field is not checked, so an older plan still runs — but the schema requires them, so new plans are covered.
- `agent/utils/robot_spec.py` loads `simulator/utils/robot_config.py` by file path (because `agent/utils` shadows the simulator's `utils` package).
- The pipeline runs one skill per invocation via `--skill "<description>" --name <NAME>` (the old batch-over-a-bundled-library mode and its `archive/` input were removed; `run.py` errors out if `--skill` is missing). `agent/agents/skill_gen/` survives that removal but only one piece of it is on the live path: `skill_formatter.py:prepare_skill` turns the free-text `--skill` into the structured dict the graph consumes. The rest (`nodes.py`, `skills_analysis.py`, `skill_clusterer.py`, driven by `agent/run_skill_gen.py`) is the separate library-*inventing* pipeline — it has no edge into `code_gen` and is not exercised by a normal run.
- **`utils/tools.py:extract_json_from_message` must be TOLERANT of routine LLM JSON quirks, because it sits on EVERY node's path** (formatter, planner, diagnosis) and a parse error there aborts the whole skill having produced nothing. It already passed `strict=False` for raw control characters; it now also strips **trailing commas** (only outside string literals) and retries once, re-raising the ORIGINAL error if that still fails so a genuinely malformed response is reported honestly. Measured: a cartwheel run died 20 s in at `prepare_skill` with "Illegal trailing comma before end of object" — zero work, one wasted invocation.

### Simulator (`simulator/`)

`simulator/run.py` → `simulator/core/`:
- `core/config.py` loads `simulator/config.yaml` (flattened into argparse-style args).
- `core/simulator.py` — MuJoCo + glfw rendering; camera framing comes from the spec.
- `core/controller.py:MotionControllerRunner` — loads the RobotSpec and resolves `--mode` in priority order: `example` → the robot's `example.py`; a **generated** skill (`skill_output/<robot>/<mode>/` holds a versioned `<mode>_<N>.py`) → the latest version; a **curated** exemplar (`robots/<robot>/exemplars/<mode>.py`) → that file; else the example. (Generated wins so the pipeline always plays its own fresh output; curated is the tracked fallback for reference skills.) Calls the skill's MotionGenerator for root pose + world/body-frame EE targets, solves IK (`utils/kinematics.py`, generic damped-least-squares over the spec's sites/joints with a null-space pull toward the standing pose, clamped to joint ranges each iteration), applies the skill's optional `joint_overrides`, and positions **mocap objects** — via `compute_object_poses(phase)` for authored paths, then overriding any `attachments(phase)`-declared object to its holders' ACHIEVED positions (auto-attach: a held object coincides with the real limbs). Several general safety nets keep grounding-off skills honest: an **IK target clamp** (no EE's sole may be authored below its surface — a swing limb can't be driven through the floor); a **floor assist** (under grounding off, lift the base so the deepest DECLARED contact rests on its surface — surface-aware, lift-only, capped 5 cm); a **reach-seat** (seat the base along z so a declared EE contact stays within limb reach — capped at `REACH_SEAT_CAP`=0.15 m, beyond which the authored base is grossly wrong and the contact is left to float VISIBLY); and a **free-EE reach projection** (`REACH_PROJ`, a free non-contact EE whose world target is beyond reach is pulled onto the reachable ball — else IK flips configs frame-to-frame, the "hand flicker"; the seam bridge re-arms on the authored TARGET jump, not tracking error, so a chronically-unreachable target no longer sawtooths). After the final FK it computes the **fundamental collision layer**: `surface_penetration` (+ localized `penetration_body`/`penetration_surface`), `self_collision`, `contact_mask`, `surface_clearance`, `object_poses`; the silent-intervention magnitudes (`clamp_mag`, `reach_seat_delta`, `floor_assist_lift`, `reach_proj`, `pin_mag`) are all recorded so the repair loop SEES what the framework corrected. End-effectors can be marked `contact: false` in the spec.
- **PHYSICAL SLEW LIMIT** — no actuated joint may change faster than its torque-derived ceiling (`dynamics.json` × dt). Applied to the **final** joint vector in `controller.step()` (after IK, after `joint_overrides`, after the seam bridge and penetration resolves), because that is the only point that sees every path that can step a joint — limiting inside the IK alone would leave a joint-driven limb free to teleport. This makes `no_teleport` **structurally impossible** rather than checked after the fact; it was the single largest consumer of the repair loop (55 archived iterations, never solved in 3 skills), and turning it on removed the teleport class from every skill that had it (13 → 1 teleport-class failures across 9 skills). It is surgically selective — ~0.07% of steps on a walk, 2.7% on a cartwheel. The trade is deliberate and **recorded** as `rate_limit_mag`: a skill demanding infeasible speed now UNDER-REACHES (a lag) instead of snapping, so the loop can see the authoring was too fast. Self-disables on a robot with no dynamics data; `RATE_LIMIT=0` for A/B.
- **Null-space reference = CONTINUITY, not home.** Position-only IK gives 3 constraints against ~7 DoF per limb, so the twist axes (`hip_z`, `shoulder_y`, `abdomen_z`) are nearly unobservable in the residual and follow the null-space reference almost entirely. Pulling them toward the *standing* pose is right for a walk and actively harmful for an inverted one, where home is maximally wrong — a cartwheel's `right_hip_z` spiked on 837 frames and **reversed direction on 21% of them**. The reference is now the previous frame's solution (which the solver already warm-starts from) with only `HOME_PULL`=0.05 pulling home so a DoF cannot drift; the skill's declared posture still wins outright. `CONTINUITY_REF=0` for A/B.
- **SINGULARITY SEED — a joint resting exactly ON its limit is unlocked before the first Jacobian is evaluated.** This was the single largest *physical* bug in the framework and it masqueraded as an authoring error for every scene and parkour skill. The humanoid's `home` keyframe puts both knees at exactly `0.0` with range `[0.0, 2.79]` and the leg perfectly straight and vertical — an **exact kinematic singularity**, because at full extension the knee axis moves the foot purely HORIZONTALLY and its Jacobian column has *zero* first-order authority over foot HEIGHT. Damped least squares therefore returns exactly zero knee correction, the leg stays locked at full extension, and **lowering the base drags the feet through the floor**. Measured in isolation: lowering the base 0.88 → 0.36 m with the feet pinned at z=0.05 left the knee at `0.000` on *every* frame and the foot 0.47 m underground (0.52 m tracking error). That is the squat/crouch/landing primitive underneath every scene-interaction and parkour skill, so it broke the carry-box (both knees held at exactly `0.0000` for 100 frames while the feet sank **0.26 m** under the floor, then snapped to 1.31 rad once the hip had rotated far enough to restore the knee's leverage — one cause producing a penetration *and* a teleport), the ledge-drop landing and the climb mantle. Biasing the null-space *reference* off the wall is **not** enough on a real skill: with hands and contact bodies also active the null-space projector squeezes that term to nothing (measured: 0.2844 → 0.2805 m, no practical change). The seed moves the **configuration**, which no projector can cancel — nudging any at-limit joint a small margin (`min(0.05 rad, 2% of range)`) inside its range, gated on there being a task error worth solving so a converged pose is never jittered, and self-correcting (the following iterations undo an unnecessary nudge, and the home pull holds a joint at its limit whenever that is genuinely right). Carry-box `surface_penetration` **0.2844 → 0.0000 m**; the knee now folds smoothly from the first frame and the feet hold z=+0.047 through the whole squat. **This also cleared a false diagnosis**: the saturated floor-assist made `framework_interventions` tell the agent *"declared contacts are authored well BELOW their surface"* when the contacts were authored correctly at z=0.05 — the solver was dragging them under, and the repair loop was being sent after a phantom.
- **EE orientation task** (`ORI_WEIGHT`, `EE_ORIENT=0` to disable) — an EE with an orientation target contributes 6 Jacobian rows instead of 3, which is what finally *observes* the twist DoFs. Two modes: `align` (put the EE's home-'up' axis along a world direction, error = `a_cur × a_tgt`, leaving rotation ABOUT that axis free) and `quat` (full 3-DoF). **A declared GROUND-CONTACT EE (`spec.contact_ee_indices`, i.e. the feet) defaults to `align` against the surface normal under it** — sole flat on a tread or a wall — while the foot's YAW stays free, which a full quaternion would wrongly pin. The auto-default is deliberately restricted to those EEs, because the alignment target is "sit the way you sit at HOME" and that is only meaningful for a member which IS flat on the ground at the home pose. It is wrong for a mid-limb contact body (a shin is vertical at home but lies flat when kneeling — auto-orienting it broke a crawl outright, 1 → 5 failing checks) and for a `contact: false` EE (the hands hang at the side at home, so a handstand's palms have no home-flat reference). A FREE limb gets nothing either: forcing orientation on a gesture would dissolve the shape the joint channel exists to preserve. Every one of those limbs can still declare an explicit attitude via `compute_ee_orientation_world_frame` — this governs only the default. Costs ~2× IK time.
- **IK backend** — `make_ik` selects via `IK_BACKEND`: `dls` (default) or `mink` (opt-in QP with joint position + velocity limits and collision avoidance as *hard* constraints; `pip install mink 'qpsolvers[daqp]'`, absent ⇒ loud fallback to DLS, never a crash). Which is better was **measured, not assumed**: mink's constraints are genuinely stronger, but its first-order velocity solve tracks the authored targets more loosely, and the contact laws score **achieved** positions — so it currently trades violations it makes impossible for a tracking lag that reads as contact drift. One real bug was fixed along the way: mink constrained *every* robot geom to stay 4 mm off every surface, which in a kinematic contact sim is a contradiction (a sole is *meant* to rest at ~0 clearance) and left the humanoid unsupported 87% of a plain walk. Contact geoms are now excluded from surface-avoidance; everything else still avoids surfaces, so a shin cannot cut through a slab.
- `utils/surfaces.py:SceneSurfaces` — **THE** scene-surface query: "what is beneath this point, and what is its normal?", answered by ray-casting each static geom (`mju_rayGeom`). **A point BURIED IN a solid is supported by THAT solid's top**, not by whatever lies below it: a downward ray fired from inside a box cannot hit the top face it is already past, so the probe used to fall through to the floor and report a buried contact as comfortably CLEAR — the exact opposite of the truth, and invisible because `contact_grounded` and `contact_no_slide` both score `surface_clearance`. Measured on the ledge drop: the right foot sits 3.6 cm INSIDE the ledge for 234 frames and was recorded as **0.664 m of clearance**, so its slide was never even measured (the "firmly planted" gate needs clearance ≤ 3.5 cm) while `surface_penetration` correctly flagged the very same frames. `support_under` now resolves the containing solid first. Exact for every primitive at any orientation, in world coordinates. It replaced five near-identical inline loops (four in `controller.py`, one in grounding) that each re-derived a box top from `model.geom_pos` with an axis-aligned test — three unstated and unenforced assumptions (BOX, AXIS-ALIGNED, declared directly in `<worldbody>`) that a ramp, a ball, or a table authored as one offset `<body>` would silently violate. Mocap bodies are excluded: a carried box is a manipuland, not a surface.
- `core/grounding.py:ContactGrounding` — the deterministic kinematic contact layer, i.e. the parts of the motion that *geometry* fixes rather than the LLM. Every height is measured against the surface actually beneath that contact, so a foot on a tread and a pelvis on a seat are ordinary cases. **Registration and pinning are independent modes**: `contact` (register the base + pin + clamp), `pin` (pin + clamp only — the skill owns its base height, right for a squat or a sit), `off` (nothing; manual playback). The contact set is **per-phase** from `contacts(phase)`, which is what lets one mechanism cover a fixed support set, a changing one (cartwheel: feet → hands → feet), and flight (`[]`). Key asymmetry: when the skill **explicitly declares** contacts they are load-bearing *by declaration* and get seated even if authored high; only the `active is None` fallback uses the "all feet well above their surfaces ⇒ probably airborne" heuristic — that is what stops a crawl whose hand/knee targets sit a few cm high from being misread as a hover.
- **Pinning is a bounded, rate-limited, recorded correction**, like every other net here (floor assist 5 cm, reach seat 15 cm). It absorbs micro-slip and IK jitter up to `pin_cap`, saturates on a contact that is genuinely moving so `contact_no_slide` still sees the skill's own error, and eases in and out rather than stepping. Its magnitude is recorded as `pin_mag`. The previous implementation hard-pinned XY and released at a 0.30 m `break_dist`; because the reference walk's `step_length` is *exactly* 0.30 m, it held the stance foot for a full stride then **snapped** it — manufacturing a joint teleport the repair loop then tried to fix in the skill rather than the framework. Its release counter was never read by anything, so the snap was invisible. Fixing this took the flat reference walk from failing `contact_no_slide` (0.106 m, and 0.307 m under the old pin) to passing the floor outright.
- `core/recorder.py` — writes two artifacts to `skill_output/<robot>/<mode>/`: `<mode>.pkl` (eval dict: `root_pos/root_quat/joints/ee_positions` (+`_achieved`) + `fps/robot/ee_names/support_ees` **plus the collision-layer arrays** `surface_penetration`, `self_collision`, `contact_mask`, `surface_clearance`, and `object_pos` — all consumed by the unit-test node) and `<mode>_mimickit.pkl` (MimicKit `{fps, loop_mode, frames}`). The capture window in `simulator/run.py` is fussier than it looks, and each part earns its place: a 50-frame **warmup**, then the skill's phase clock is reset to 0 and the seam bridge cleared; then a 0.3 s **settle window** that pins phase at 0 while IK converges from the warmup pose to the exact phase-0 pose (without it the *achieved* contacts drag toward their pins over the first ~0.1 s of the recording and read as a phantom `contact_no_slide` drift); then `record_cycles / skill_freq * sim_freq` frames. Recording length uses **the skill's own `freq`**, not the config's, so a slow skill is captured in full instead of truncated. The settle bound is inclusive (`<= start_frame`) because `base.step()` reads `t` then increments it — off by one and the last recorded frame lands on phase 1.0, which wraps to 0 and snaps a one-shot skill's final frame back to its start pose, manufacturing a fake "0 cm net motion", a phantom stance-foot slide, and a seam teleport that then poisons the repair loop.

- `utils/reach.py` — the shared limb-reach model (base → tip length per limb). `controller.py`'s reach-seat / reach-projection, `tools/reach_lint.py`, and `{robot_summary}` all consume it, so the pre-sim lint's verdict and the runtime's behaviour cannot disagree.
- `tools/` — all offline or debug, never on the inner loop: `gen_robot_spec.py` and `gen_robot_summary.py` (run once per new robot), `reach_lint.py` (called per iteration by the agent, but as a subprocess oracle), `record_video.py` (the finalize preview GIF, also usable by hand), `pose_editor.py` (interactive stance authoring). `reach_lint` and `record_video` both instantiate the real `MotionControllerRunner`, which is the point — a debug tool that models the sim separately would drift from it. **`reach_lint` FAILS OPEN on any exception and that must stay LOUD.** Never crashing the pipeline is the right robustness choice, but a silently-disabled safety check is worse than no safety check: the loop, the logs and the reader all believe the version was screened when it was not, and 'no report' looks identical to 'passed' downstream (both return None, both proceed to the rollout). Measured: a `TypeError` inside the surface-existence check disabled the ENTIRE lint, and a ledge-drop standing 0.75 m up on empty air sailed through to the sim and SHIPPED, while the run log said only 'proceeding to sim'. A no-report outcome now prints an explicit UNSCREENED warning with the subprocess's last stderr line. When invoking it BY HAND, pass `--scene` — `_resolve_scene_grounding` only auto-resolves a scene for registered *exemplars*, so a generated skill silently falls back to `flat.xml` and every surface answer is then wrong.

### Skills & the framework (`simulator/motion/`)

- `simulator/motion/__init__.py` — the loader. `get_motion_controller(skill, gaits_dir)` imports the **highest-numbered** `<skill>/<skill>_<N>.py` from `skill_output/<robot>/` (generated); `get_curated_controller(path)` loads a single-file `robots/<robot>/exemplars/<name>.py` (hand-authored); `get_example_controller(path)` loads a robot's reference `example.py`. `has_skill_version(gaits_dir, skill)` tells a real generated skill from a leftover artifact-only dir. All return the first concrete class whose name ends in `MotionGenerator`.
- All skills subclass `simulator/motion/base.py:BaseMotionGenerator`. Contract: `__init__(init_ee_pos: dict[name → body-frame pos], freq)`. **Three control channels, chosen per limb per phase by the agent** — the discriminator is COUPLING, not the limb (nothing prescribes a fixed channel): (1) WORLD-frame IK — `compute_ee_position_world_frame(ee, phase)` for a position the WORLD fixes (a contact on a surface, or a limb that must COINCIDE with an object it grips/holds). (2) BODY-frame IK — `compute_ee_position_body_frame(ee, phase)` for a target relative to the torso (a swing foot). Both solve IK; **both default to `None`, which makes IK SKIP that EE**. (3) JOINT — `compute_joint_overrides(phase)` returns `{joint: angle}` set directly, for a limb whose configuration is the point and whose endpoint is unconstrained (a gesture, a kick). **`init_ee_pos` and these channels span the UNION IK ROSTER** (EEs + declared `contact_bodies`), so a mid-limb contact body (a knee/forearm) is placed by returning its world contact point (IK bends the limb to it) — it is no longer FK-only. The reach-seat/reach-projection stay EE-only (their base→tip reach model is meaningless for a mid-limb body); a mislaced contact body simply floats and `contact_grounded` catches it. Also `contacts(phase)` → per-phase load-bearing EE names (`[]` = ballistic flight — **declare precise per-phase contacts, not a static support set**); `compute_object_poses(phase)` → `{name:(world_pos,quat)}` for object paths; and **`attachments(phase)` → `{object: [ee,...]}`** — declares an object rigidly HELD by end-effectors, and the framework places it at the holders' **ACHIEVED (post-IK) positions** so a grip is correct BY CONSTRUCTION (no open-loop guessing). EE targets in **body OR world frame**, base pose in **world frame**, phase ∈ [0,1] (cyclic OR one-shot). This file's source is injected into the coder prompt — keep its docstrings accurate. Skills import `from motion.base import BaseMotionGenerator`.
- **Curated vs generated (separated):** a small number of hand-authored reference skills are tracked as `robots/<name>/exemplars/<NAME>.py` and registered in `robot.yaml`'s `exemplars`; agent-generated output lives in gitignored `skill_output/<robot>/` (regenerable). `robots/<name>/example.py` is the default demo (a walk). The humanoid ships 2 exemplars (`SKILL_CLIMB`, `SKILL_CARRYBOX`) — deliberately minimal, not a skill library. An environment's `grounding` MUST match how its skill authors the base: `off` for skills that set an absolute base + world-frame contacts (stairs/climb/carrybox — raised or object surfaces the flat re-seat can't express), `contact` for flat-floor skills that let the framework re-seat. **Migrating the scene environments to `pin` was measured and REJECTED.** It looked like a free win while the IK singularity bug was live (carry-box 4 → 2 failures) — but pinning was only compensating for feet the *solver* was dragging through the floor. Re-measured with the singularity fixed at source, `pin` is a net loss across the five scene skills: 1 win (carrybox −4.50 → −3.50) against 3 losses (climb −3.00 → −4.00, breaking `self_collision`; ledge-drop −3.00 → −4.50, breaking `contact_no_slide` and dropping a fidelity invariant; sit-chair −2.00 → −3.50, breaking `contact_grounded` and dropping one). Do not re-litigate this without re-running the A/B — the lesson is that a grounding-layer "win" can be masking a solver bug.

### Environment interaction (objects in the scene)

Skills can interact with scene objects (a climb slab, a carry box):
- **Scene override**: `python simulator/run.py ... --scene assets/scenes/slab.xml` loads a scene with objects instead of the robot's default bare floor. `slab.xml` adds a static half-height slab; `stairs.xml` a staircase; `chair.xml` a seat + backrest; `carry.xml` a **mocap** box. Static object geoms sit in the worldbody (bodyid 0), so they are auto-excluded from the robot penetration checks. The exact geometry of each is parsed and injected into the prompts (`agent/utils/scene_geometry.py`) — never hand-described, so the agent targets real surface heights.
- **ATTACHMENT PROXIMITY GATE — a declaration is not a grip.** `attachments()` used to snap the object to its holders' achieved positions UNCONDITIONALLY, which makes a grip true by construction even when the limbs never arrived. That does not merely hide the error, it **MANUFACTURES a physically impossible object trajectory in the recorded training data**: measured on a carry-box, the hands bottomed out at z=0.448 while the crate's grip faces sat at 0.12, and the crate LEVITATED 0.12 → 0.64 m to meet them, recorded as ground truth. Every other correction here is bounded, recorded and surfaced (clamp 45 cm, floor assist 5 cm, reach seat 15 cm); this one was unbounded and silent. Now the attach only happens when the holders are within `object half-extent + GRIP_SLACK_M` (0.12 m) of where the object **physically was last frame** — deliberately NOT this frame's authored pose, because a skill that both animates the object and declares it held drives it toward the hands itself, making that comparison trivially self-consistent (measured: the gate never fired). Out of range ⇒ the object is left alone, the miss is VISIBLE, and `object_grip` scores the real failure. Magnitude recorded as `attach_miss` and surfaced by `framework_interventions`.
- **Object animation**: a skill's `compute_object_poses(phase)` returns `{name: (pos, quat)}` for **mocap** bodies; `controller.step()` writes `data.mocap_pos/mocap_quat`. The sim is kinematic (no grasp physics), so a carried box is simply placed where the hands are while held — and `attachments(phase)` makes that automatic by snapping the object to its holders' *achieved* positions. Reference: `robots/humanoid/exemplars/SKILL_CARRYBOX.py` (box tracks the hands during pick→carry→place).
- **Two contact heights**: when contacts live at floor z=0 AND an object surface (a slab top at z=0.44), the flat-floor grounding cannot express it — author the whole trajectory in **world frame** and run with `--grounding off` (the base height and every contact are placed explicitly). Reference: `robots/humanoid/exemplars/SKILL_CLIMB.py` (climbs onto the slab). These skills *are* scored now: `contact_grounded` reads the recorded `surface_clearance` (EE → nearest surface below) rather than a hardcoded z=0, so a contact on a tread/ledge/seat counts as grounded, and `surface_penetration` tests robot geoms against static scene boxes as well as the floor. The pre-sim reach lint runs in **both** grounding modes — its arrival check applies to any skill; only its reachability check self-gates to `grounding: off`.

### Adding a robot

1. Drop the MuJoCo model + meshes under `assets/robots/<name>/`. **MJCF format standard** (makes the spec auto-scaffoldable and the physics/dynamics extractable): the root body carries the `<freejoint>`; each end-effector body has a `<site name="ee_<name>"/>` (marks it as an EE for auto-detection AND gives IK a real target — no site = IK falls back to the body center); each actuated joint has a `range` (position limits) + `actuatorfrcrange` (torque, N·m); passive joints have no actuator; a `<keyframe name="home">` holds the rest pose; mass/inertia come from `<inertial>` tags or geom density.
2. **Auto-scaffold the spec**: `python simulator/tools/gen_robot_spec.py --robot <name>` → writes `robots/<name>/robot.yaml`. Exact from the MJCF: `joints` (qpos[7:] order + limits), `base_body`, passive flags, `robot_card`, paths. `# REVIEW`-marked guesses to check: `end_effectors` (from `ee_*` sites, else a leaf-body heuristic — fix the order/`ground_offset`/`contact` flags), `base_height_range`, `camera`. Then write `example.py` (a `BaseMotionGenerator` subclass — the reference demo) and fill `environments:`/`exemplars:` as you author scenes/skills (not derivable).
3. Generate the physical summary + machine-readable ceilings: `python simulator/tools/gen_robot_summary.py --robot <name>` → `robots/<name>/summary.md` (injected as `{robot_summary}`) + `robots/<name>/dynamics.json` (per-joint velocity/accel ceilings for the `joint_velocity_envelope` check). The **dynamics tier is automatic** — emitted when the MJCF carries mass/inertia and a torque source, else skipped (both `{robot_summary}` and the velocity check then self-omit; the robot still runs). Override with `--no-dynamics` / `--dynamics`.
4. Set `robot.name` in `agent/cfg/config.yaml`. No prompt or code changes needed. `python simulator/run.py --robot <name>` plays the example immediately (it composes the model with `assets/scenes/flat.xml`).

Scenes are **shared and robot-agnostic** (`assets/scenes/*.xml`, floor + objects only). To give a skill a new object, add `assets/scenes/<env>.xml` (a mocap body for a carried item, a static geom for a fixed one) and register it under `environments:` in `robot.yaml` — the planner picks from registered environments, and a request for an unregistered one prints a `⚠️ MISSING ASSET` warning telling you to add it.
